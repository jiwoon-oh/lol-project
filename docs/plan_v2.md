## 8. 에이전트 실행 방식과 시간

**지금(v1) 방식**: 메인 대화가 하위 에이전트를 **여러 개 동시에(병렬)** 띄움. 각 에이전트 **안에서는** 묶음을 하나씩 차례로(직렬) 읽고 씀.

| 단계 | 에이전트 | 실제 걸린 시간 |
|---|---|---|
| S4 도란 | 4개 동시 (각자 묶음 4~9개를 차례로) | 약 3분 (172초) |
| S4 오너+페이커 | 8개 동시 | 약 3.5분 (209초) |
| S6 오너 | 1개 | 약 2.6분 |

→ 에이전트끼리는 이미 병렬. 직렬이었던 건 ① 에이전트 안의 묶음 처리 ② 선수 순서(도란 먼저 → 확인 → 오너·페이커)

**v2 방식**: 에이전트 하나가 묶음 8개를 **한 번에** 읽고 한 번에 씀 (에이전트 안 직렬 단계가 없어짐). 에이전트끼리는 병렬.

| 단계 | v2 직렬 실행 (선수 차례로) | v2 병렬 실행 (3명 동시) |
|---|---|---|
| 수집: S1 뉴스·영어 | 약 1~2분 | 같음 |
| 수집: S2 본문 (약 210건, 여러 사이트) | 약 3~5분 | 같음 (같은 사이트 요청 간격 1~2초는 지켜야 해서 사이트 안은 병렬로 못 함) |
| 수집: OP.GG 목록 + 본문 (약 400건) | 목록 쪽수에 달림 (예: 2,000쪽 + 400건 ≈ 60분) | S1·S2와 **동시에** 돌릴 수 있음 (다른 사이트). 총 수집 시간 ≈ OP.GG 시간 |
| S3 표본 | 약 1분 | 같음 |
| S4 (선수당 에이전트 약 3개) | 선수당 약 3~5분 × 3 = 약 10~15분 | **약 3~5분** (에이전트 약 9개 동시) |
| S5 | 1분 미만 | 같음 |
| S6 (선수당 1개) | 약 3분 × 3 = 약 9분 | **약 3분** |
| **LLM 단계 합계** | **약 20~25분** | **약 6~8분** |

- 토큰 총량은 병렬이든 직렬이든 같음. 병렬은 같은 시간에 구독 사용량을 빨리 씀 → 한도에 닿으면 대기 발생 가능
- 계획의 "도란 먼저 확인" 멈춤 지점을 없애면 3명 병렬 가능. 대신 지시문에 문제가 있으면 3명 몫 토큰을 한꺼번에 낭비 → **권장: 도란 S4 먼저(약 3~5분) 확인 후 오너·페이커 병렬**, S6는 3명 병렬
- 시간 대부분은 OP.GG 수집(요청 간격 규칙 때문). 1단계 시험에서 쪽당 기간을 보고 예상 시간을 다시 계산

## 10. 토큰이 떨어졌을 때 (자세한 절차: `docs/runbook.md`)

- **상한**: `budget.yaml` `run.token_cap` = 130만 (계획 추정 80만~110만 + 여유). 누적 + 다음 작업 예상이 90%(117만)를 넘으면 새 에이전트를 띄우지 않고 멈춰서 보고
- **기록**: 에이전트가 끝날 때마다 `usage.csv`에 run=`v2`로 기록 (v1 기록은 run=`v1`, 상한 계산에서 제외)
- **구독 한도에 막히면**: 끝난 에이전트 결과 파일은 남고, 멈춘 에이전트 몫(최대 약 96건)만 다시 돌림. `runctl.py status`가 다시 돌릴 에이전트를 알려 줌
- **실수 방지**: 결과 파일이 있으면 `extract_claims.py prepare`가 거부 (끝난 결과를 지우지 않게)
- **수집 단계**(토큰 0)도 끊기면 이어서: S2·OP.GG는 받은 것 건너뜀, OP.GG 목록은 마지막 쪽 다음부터
